# Health Insurance Coverage Assistant (RAG)

Ask plain-English questions about a health plan ("What do I pay for a specialist visit?", "How long do I have to
appeal a denial?") and get a short answer **with numbered citations to the exact plan page and section**, or an explicit
"I could not find this in the plan documents."

**Docling** parses the plan PDFs, **PostgreSQL + pgvector** stores the chunks (HNSW vector index and a full-text
index in one database), and an open LLM served by **vLLM** writes the answer from the retrieved excerpts only.

> **Status.** Everything except the real models is built and tested here against a real PostgreSQL 16 + pgvector
> server. **Docling, the embedding model and vLLM were never run** (the build sandbox has no GPU and cannot reach
> Hugging Face), so the repo has **no answer-quality numbers for a real model**. Test documents are two *fictional*
> plans generated by `insurance_rag/sample_docs.py`. This is an information tool, not a coverage determination or
> medical/legal advice.

```
plan PDFs ─▶ Docling (layout, tables, headings, pages) ─▶ chunks ─▶ embeddings ─▶ pgvector table
                                                                                       │
question ─▶ embed ─▶ ┌ vector search (HNSW, cosine) ┐                                  │
                     └ keyword search (tsvector)    ┘ ─▶ Reciprocal Rank Fusion ◀─────┘  (optional plan filter)
                                                              │
                               top-k excerpts ─▶ vLLM (cite [n] or refuse) ─▶ citation check ─▶ JSON answer + sources
```

## Design decisions (and why)
- **Hybrid retrieval.** Embeddings match paraphrases; Postgres full-text search matches exact tokens (dollar amounts,
  drug and procedure names). Rank lists are merged with Reciprocal Rank Fusion (1/(60+rank)), which needs no score calibration.
- **Plan filter.** Plans from one insurer read almost identically, so a question like "specialist copay" retrieves
  the wrong plan's number unless the search is restricted. `plan` is a column and an optional filter on every query.
- **Chunks follow the document's structure**: never across a section or page, never splitting a table row; the heading path
  is stored, indexed, and prepended to the embedded text. Docling's `HybridChunker` does this for real PDFs; a heading-aware
  chunker covers the pypdf fallback.
- **Grounding rules in code, not just in the prompt.** The prompt forces `[n]` citations and an exact refusal sentence;
  `answer.py` then checks every cited number exists (catches invented citations), flags uncited answers, detects
  refusals, and can skip the LLM entirely when retrieval looks irrelevant (`min_cosine`, needs per-model calibration).
- **Idempotent ingestion** (re-ingesting a document replaces its chunks) and a hard check that the table's vector size
  matches the embedder.

## Run it

```bash
python -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
docker compose up -d                       # PostgreSQL 16 + pgvector on :5432 (user/password/db: rag/rag/ragtest)
python -m pytest tests -q                  # 36 tests; DB tests need the server above (skipped without it)

# Demo with fictional plans and stand-in components (no models, no GPU):
python -m insurance_rag.sample_docs --out data/sample
python -m insurance_rag.ingest --pdf "data/sample/cedar_silver_3000.pdf::Cedar Silver 3000" \
       --pdf "data/sample/cedar_gold_1000.pdf::Cedar Gold 1000" --parser pypdf --embedder hash --recreate
python -m insurance_rag.evaluate --eval data/sample/eval.jsonl --embedder hash --llm none     # retrieval metrics only
```

### With the real models (what you need to do; untested here)
```bash
pip install -r requirements-models.txt                      # docling, sentence-transformers
# separate env for the LLM server (GPU):  pip install -r requirements-vllm.txt && bash scripts/serve_vllm.sh
python -m insurance_rag.ingest --pdf "plans/your_sbc.pdf::Your Plan 2025" --parser docling --embedder st --recreate
EMBEDDER=st LLM_URL=http://localhost:8000 uvicorn insurance_rag.api:create_app --factory --port 8080
curl -X POST localhost:8080/ask -H 'content-type: application/json' \
     -d '{"question":"How much is the ER copay?","plan":"Your Plan 2025"}'
python -m insurance_rag.evaluate --eval your_eval.jsonl --embedder st --llm vllm       # full retrieval + answer metrics
```
Defaults: embeddings `intfloat/e5-base-v2` (MIT, Microsoft), LLM `microsoft/Phi-3.5-mini-instruct` (MIT); both
configurable. Real plan documents: insurers publish Summary of Benefits and Coverage PDFs; check their terms of use.
Do not load documents containing a member's personal health information into a shared or cloud database.
To measure real quality, write an eval set in the format of `data/sample/eval.jsonl` from your own PDFs (question,
plan, the exact fact strings the answer must contain), ideally 100+ questions including unanswerable ones.
Postgres on a cluster like HiPerGator would need an Apptainer image or a service you reach over the network; not tried.

`eval/dol_eval.jsonl` is the eval set for the two Department of Labor sample SBCs (`sbc-completed-sample-2/3.pdf`, plan names
"Sample Plan 2" / "Sample Plan 3"): 53 answerable questions and 12 unanswerable ones. Every gold fact was checked to sit inside a single
Docling chunk of its own plan. The two plans are nearly identical (same deductible, copays and limits), so the plan filter is tested
only through the "right plan" criterion, and the plans are fictional "Insurance Company 1" samples, not real insurers. The two samples
have 65 questions in total, which is small: expect wide uncertainty on any percentage, and do not quote one to more than whole percents.

Public, redistributable test documents: the U.S. Department of Labor publishes fictional "Sample Completed SBC" PDFs
(dol.gov, search "sample completed SBC"); real insurers' SBCs are also public but check their terms before committing them.

## What the evaluation measures
`evaluate.py` reports, per retrieval mode (vector, keyword, hybrid): **Recall@1/3/5** and **MRR** (an answer-bearing chunk
from the right plan in the top k); and for answers: **fact_match**, **valid_citations**, **cited_supported**,
**grounded_correct** (states the facts *and* cites a chunk containing them), **false_refusal** on answerable questions,
**correct_refusal** on unanswerable ones, and retrieval/LLM latency p50/p95. These are string-match proxies: strict, cheap
and reproducible, but they miss correct paraphrases ("thirty dollars") and don't judge fluency.

## Results (real run: Docling, e5-base-v2, pgvector, Phi-3.5-mini-instruct on vLLM)
Corpus: two fictional U.S. Department of Labor sample SBC plans, 55 chunks. Eval set: 65 hand-written questions
(53 answerable, 12 unanswerable), `eval/dol_eval.jsonl`. **Small and single-corpus: these numbers show the pipeline
works and where it fails, not how it would do on real insurer documents.**

Retrieval (answer-bearing chunk of the right plan in the top k, n = 53):

| mode | Recall@1 | Recall@5 | MRR |
|---|---|---|---|
| vector (plan filter) | 0.774 | 0.925 | 0.838 |
| keyword (plan filter) | 0.509 | 0.774 | 0.617 |
| hybrid / RRF (plan filter) | 0.679 | 0.925 | 0.780 |
| hybrid, **no** plan filter | 0.340 | 0.830 | 0.553 |

Vector alone beat hybrid on Recall@1 and MRR here, so hybrid is not claimed to be better. The plan filter roughly
doubled hybrid Recall@1 (0.34 -> 0.68), because the two plans are nearly identical.

Generation (hybrid retrieval, top 5; `reports/eval_generation_v2.json`):

| metric | value |
|---|---|
| fact_match (answer states the value) | 0.868 (46/53) |
| valid_citations | 0.830 |
| cited_supported (cites the labelled chunk) | 0.547 |
| grounded_correct (right value and cited chunk supports it) | 0.547 (29/53) |
| false refusal, exact sentence / loose | 0.038 / 0.113 |
| correct refusal on unanswerable, exact sentence / loose | 0.167 / 1.000 |
| retrieval p50 / p95 | 7.0 ms / 7.2 ms |
| LLM p50 / p95 (one request at a time) | 106 ms / 284 ms |

How to read these:
- **The eval was revised after seeing a first run.** Run 1 used `facts` for both locating the chunk and judging the
  answer, and counted only the exact refusal sentence. It scored fact_match 0.358 and grounded_correct 0.264. Much of
  that was measurement (labels such as "Primary care" had to appear in the answer, and paraphrased refusals did not
  count), so v2 judges answers on `answer_facts` (values only) and adds loose refusal metrics. The jump from 0.358 to
  0.868 is mostly a change in the metric, **not a better model**. Both runs used the same model and prompt. The 65
  questions were also used to find these problems, so they act as a dev set, not a held-out test.
- **Real failures:** the out-of-pocket-limit questions were answered "not specified" in both plans (4 of the 53; the model
  also failed one facility-fee question in plan 3). In answers that state the right value, 11 cite an excerpt that is not the labelled
  one and 6 use an invalid citation format or index, which is why grounded_correct is far below fact_match.
- **Refusals:** 10 of 12 unanswerable questions were declined in the model's own words rather than the exact
  sentence, so the strict number (0.167) understates it; the loose number (1.000) is the better reading. Caveat: the
  loose detector has false positives. One real answer ("does not include copayments...") is counted as declined, so the
  true loose false-refusal rate is 5/53 = 0.094, not 0.113.
- `cited_supported` requires the cited excerpt to be the labelled chunk; I have not checked how many of the 11 misses
  are cited excerpts that also support the answer.

## Verified vs not verified

**Verified by running it (39 tests, a live run, and deliberately breaking code to confirm tests fail):**
- Real PostgreSQL 16 + pgvector 0.6.0: schema, HNSW and GIN indexes, cosine search returns the hand-computed order and
  scores, plan filtering, exact-vs-index agreement on a small set, idempotent re-ingest, dimension-mismatch rejection,
  keyword search with headings indexed, stop-word-only and hostile query strings handled. (Building it caught a real bug:
  Postgres rejected the generated `tsvector` column until headings were stored as plain text.)
- Reciprocal Rank Fusion against hand-computed scores; hybrid vs vector-only vs keyword-only modes.
- PDF text extraction (pypdf) and heading/page-aware chunking on generated PDFs; every gold fact in the eval set is
  confirmed to be in its own plan's PDF, so the eval can't drift from the documents.
- The LLM client against mocked HTTP responses (success, 500, malformed, empty, connection refused); the API (validation,
  unknown plan, LLM-down -> 502); the full chain over real sockets: API -> pgvector -> a fake OpenAI-style server.
- The metrics code against scripted answerers with exactly-known outcomes (perfect, always-wrong, fluent-but-wrong-number,
  refuse-everything). The headline metric correctly scores a fluent answer with the wrong number as wrong.
- Breaking RRF scoring, the plan filter, and citation range checks each made tests fail.

**Not verified:**
- **Docling, e5-base-v2 and vLLM have now run** (see Results). The unit tests still use a scripted LLM and a hashing
  embedder; the real-model numbers come from one run on two plans and one 65-question set, with no repeats or variance
  estimate (single run, one model, one prompt, no seeds varied).
- Real insurer PDFs: scanned documents (no OCR path in the pypdf fallback), complex multi-column tables, very long
  policies; behaviour with thousands of chunks (HNSW parameters untuned: pgvector defaults, `ef_search=100`).
- `docker-compose.yml`, GPU memory and throughput under concurrent load (latency above is one request at a time).

## Known limitations
- Heading detection in the fallback chunker is heuristic (ALL-CAPS, numbered, or Markdown headings).
- The refusal check is a substring match on the exact refusal sentence; a model that paraphrases a refusal will be
  treated as an answer without citations (flagged `uncited`).
- No re-ranker, no query rewriting, no conversation memory, no authentication on the API.
